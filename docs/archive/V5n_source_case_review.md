# V5n 源码与五个真实案例复核

## 结论与证据边界

上一轮把“右路威胁进入防守预算太晚”放在总解释的首位，范围过大。应修正为：这是一个确实存在的机制，但“有防守部署、仍持续失血”还涉及牌型适配、友军实际行进方向、既有锁定、输出形成时间，以及两路费用分配。日志中的 `confirmed=true` 是输入/扣费确认，不是功能性防守确认。

本次实际读取 ZIP 的 README、七个运行源文件中的相关执行/识别路径、五个测试文件、参考统计和五案例事件；逐图查看 44 张冻结原图。输入 ZIP 完整性检查通过，manifest 所列 92 个条目的 SHA-256 全部一致。没有连接用户 Windows、MEmu 或 ADB，也没有启动机器人。

`early-half-tower-losses-02-through-14.json` 有 63 条可读半血败局；本次重算得到 45 秒内 42 条，其中右塔 30、左塔 12。README 中“这 30 局此前有右路 far 30 局、near 27 局、15 秒内右路 defense 23 局”是用户全日志回查结果。本包只带五个精选案例的精简事件，没有这 30 局全部之前的原始事件；因此本次未独立逐局重算 23/30，也不能把五案例按比例外推成 23 局的败因分布。

注意：`category=defense` 也包括冰人、骷髅兵和冰精灵等动作；法术另记 `spell`，中央后置火枪可能记 `cycle`。这个分类本身既不是输出能力指标，也不是所有防守作用的完整集合。

## 一、五案例的修订诊断

### 案例 01：敌半场静止 X-Bow，不能靠提前炮概括

来源 `cases/01-static-xbow-right/`，历史版本 V5m。五条精选事件、八张原图。

09:45:52 的可见远端标记在 `(306,205)`，己方右塔数字 4270；09:45:56 的动作是左桥野猪，09:45:59 是左后置骷髅过牌，09:46:02 是左炮。后面的原图右塔已经降到 2345，敌方右侧弩仍在原位置输出。

源码有三个独立门槛使它不成为常规防守目标：普通 `OWN_PRESSURE_Y=300`；持续桥区观察只接收 `250<=y<300`；深色候选要求向我方位移。`y=205` 的静止源不满足。单个远端预警只在圣水不足八费时拦住部分进攻，故八费左猪仍可发生。

这个案例确实支持静止远程源缺口，但不能证明“一张新炮就能转移已经锁定我塔的攻击”。也不能以同一局八张图当作八个独立场次，直接宣布通用建筑识别已验证。

本补丁只记录 `unresolved_remote_damage` 并短暂保护费用：有连续塔伤而无同路近场压力时，最长三秒保守等待，随后允许原有候选动作、要求进攻/过牌保留四费，避免无限等待。没有自动识别弩或自动对它施法。第一张右塔填充为 `None`，所以仅凭本包给出的前两张图，补丁仍不能证明第一次左猪发生前已持续掉血；新增测试明确保留这个限制。

### 案例 02：向右路“下过防守牌”，不等于右路建立了有效输出

来源 `cases/02-mixed-right-push/`，历史版本 V5l。六条精选事件、十一张原图。

| 事件时间 | 原动作 | 原图/输入支持的判断 |
|---|---|---|
| 08:47:15 | 中央火枪 `(209,392)`，`category=cycle` | 后续图中火枪已向左路推进，不能把这张牌继续视为右路持续输出。 |
| 08:47:22 | 右路防守名义下的冰人牵引，落点 `(187,348)` | 后续冰人实际走向左侧；右塔旁地面目标保持在近似位置。不能以该动作确认成功推断牵引已成功。 |
| 08:47:26 | 冰精灵 `(282,349)` | 属于低费拖延，而不是持续输出确认。输入中深处 `(305,348)` 与桥区 `(310,250)` 是相距较远的两个观察点。 |
| 08:47:29 | 右炮 `(245,330)` | 下炮前图右塔数字已为 2580；后图不能证明贴塔地面目标已转向炮。 |
| 08:47:31 | 右滚木 | 后续右塔数字可读到 2119。此处还存在空中目标，地面处理并不等于解决整个推进。 |

当前检测器对这些关键帧输出的 `threats` 仍为空。也就是说，这是“原图中看得到混合推进，但机器仍主要只有位置标签”的案例。若机器没获得空中类别，现有“确认空中优先火枪”规则根本没有触发依据。

另外，`record()` 只把 `category=defense` 的炮/火枪登记进同路核心记录。中央火枪是 `cycle`，并不会被登记成两路防守核心。日志里的“中央火枪先建立两路输出”既缺少持续跟踪支持，在这里也与后续实际行进方向不符。

本补丁没有新建空军分类器、没有声称解决该混合推进。它修复一处相邻问题：用于滚木兜底的门槛由同路标记总数改为同一几何簇的标记数，防止塔旁一个目标与很远的桥区目标凑成“群”。新的真实帧测试要求它不把 `(305,348)` 和 `(310,250)` 拼成滚木密集目标；这只是防回归，不是证明冰精灵一定能守住。

### 案例 03：最后四费分配，当前 V5n 已有针对性修补

来源 `cases/03-split-push-last-four/`，历史版本 V5i，不是当前 V5n。两条动作、四张图。

06:16:04 右侧火枪已部署；06:16:07 右侧三标记更深，左侧另有三个临近河道标记，原策略把最后四费用于右火球。该事件支持跨路费用分配失当，而不是笼统的“没有看到左路”。

当前 V5n 已有“本路近期火枪、另一侧至少三个临近河道标记、炮可用”特例。本次用真实图及历史火枪确认记录做条件回放，保留结果为左炮 `(173,330)`，留下 1 费。这个行为不是本轮首次实现，不能把它计成本补丁的新胜率贡献。

四张图不足以完整评价该局后续，也不能把这个窄特例当成已经完成一般化的双路费用可行性规划。

### 案例 05：右塔已经失血，但右侧桥区源仍被排除

来源 `cases/05-right-collapse-split/`，历史版本就是当前 V5n。五条事件、八张原图。

10:51:11 左侧有三个远端标记，右侧一个桥区标记，机器人先左火枪。10:51:15 的关键图：右塔填充从 0.975 降至 0.671，右侧标记 `(289,290)` 仍可见；左側标记 `(111,310)` 刚越过普通压力门槛。原动作是左炮 `(173,330)`。

这里的源码路径可以明确定位：普通压力截取 `y>=300`，右侧因 `y=290` 暂时出局；选路权重只能在剩余点中计算，所以左路成为主要防守路。即便右路塔伤标志已经被设置，旧代码也主要在选路之后才读所选路的塔伤，用于打断局部等待；它不会因此把右侧目标自动纳入压力。

10:51:21 终于右火球，原图右塔已为 1044；随后为 706。该证据支持“看到了，却没有把正在造成损失的桥区目标及时纳入有效决策”。它不只是“再提前下炮”。

补丁在有可读塔伤、当前同路标记仍可见时，把 `250<=y<300` 的桥区点纳入压力；在没有更深的既有危机时优先受损路。条件回放在 7 费关键帧选择右火球 `(289,300)`，保留 3 费，沿用现有桥区减压法术逻辑。

这个测试证明候选不再重复该时刻的左炮选择；没有证明这发提前火球能击杀目标、止住全部塔伤或赢下对局。同路塔伤与桥区目标的同时出现，仍是一条启发式，不是对所有未来场景都已确认攻击因果。

### 案例 04：进攻反馈缺失，但不能把六次野猪算成六次完全空打

来源 `cases/04-six-hogs-zero-spells/`，历史版本 V5j。

完整动作摘要有 32 次：17 cycle、9 defense、6 attack，0 spell；确认野猪 6 次。所选野猪动作前图中敌左塔数字依次可读为 4032、3571、2649、2649、2527、2527。故证据支持中后段伤害停滞与没有法术支援，而不支持“六次全部未造成伤害”。敌左塔的变化也不能全部归因于野猪。

打包的是下猪前后短窗口，并非每次野猪接敌、被什么单位或建筑拦住的完整过程。第一版不据此自动为每次野猪追加四费火球；那会把缺少识别反馈的问题变成另一个盲目花费问题。进攻角色跟踪与适配支援应独立建立真实接敌窗口后再做。

## 二、最重要的源码发现

以下行号指 ZIP 中原始 V5n 文件，不是修改后的行号。

| 位置 | 发现 | 本轮处理 |
|---|---|---|
| `hog_cycle_strategy.py:225–233` 附近 | 只比较本次与上次可读塔血填充，单次下降至少 0.06 才记损伤；每步小于阈值的连续下跌可能永远不触发。 | 六秒窗口累计下降；未知/非法值及长缺口断开；低血稳定时不无限续期；明显向上跳变重设基线。 |
| `hog_cycle_strategy.py:294–328` 附近 | 普通压力和早期类别/持久桥区门槛，未覆盖“塔已掉血、目标仍在 y290”的重要组合。 | 当前可见桥区点＋同路损伤可立即进入防守；不使用消失旧坐标。 |
| `hog_cycle_strategy.py:363–405` | 先按深度/数量选路，塔伤不是通用选路输入；部分跨路规则还依据近期部署记录。 | 无更深危机时优先有当前目标的受损路，避免普通增援把它再次覆盖掉。 |
| `hog_cycle_strategy.py:458–470` | 十秒内火枪记录可授权“通用输出覆盖”反打；没有单位存活/命中检测。 | 持续塔伤时撤销这个进攻许可；但未完成真正的友军跟踪。 |
| `hog_cycle_strategy.py:644–647` 附近 | 用同路总标记数触发滚木，实际瞄准的簇可能只有一个点。 | 要求同一簇满足数量条件。它仍不是地面类别确认。 |
| `hog_cycle_strategy.py:838–849` | 确认后记卡牌与核心支出；`last_attempt` 无论成功失败都会推进。 | 保留确认与冷却语义；不将记录转换成“已经牵引/输出”。 |
| `cn_1v1_loop.py:428–447` | 已读取 after_frame、after_cues，却只拿来判断下牌是否成功。 | 抽出无动作的 `observe()`，在确认期间更新同一策略的两路观察。 |
| `cn_1v1_loop.py:403–410` | 可选技能只避让进攻跟猪，没有明确避让已选中的防守/法术。 | 技能不再抢占这些动作，也不在近期塔伤时优先花费。未放宽技能识别条件。 |

源码确认后 `record()` 才设置 `last_attempt`，下一动作还要满足 1.2 秒最小间隔。因此用户提到的“出牌与确认约 1.2 秒”，不能直接等同于“每 1.2 秒必能完成一个新防守”。本轮保留这一安全节流，没有声称缩短部署/确认物理延迟。

上述损伤反馈不是准确 HP；0.06 表示填充比例下降六个百分点。它继承既有读条器的误差风险，不能当精确伤害计量或敌方攻击来源证明。

## 三、补丁的实际范围与保护条件

候选：`hog-v5o1-damage-feedback-review-20260927`。只改两个运行文件。

1. `observe()` 不接收出牌授权，不点击、不扣预算、不确认部署。`decide()` 复用同一次观测结果。主帧与确认帧都传入像素 SHA-256，相同像素保守地不重复计入新帧；这也可能把真实重新抓取但像素完全相同的帧当重复，因此是防重复措施，不是精确的采集时间计量。
2. 累计塔伤在可读短窗口内建立。未知、零、越界、NaN 不变成伤害；长期缺图后不把旧差值归给当前帧；同一低血值不能不断刷新告警。
3. 只有当前仍可见的桥区点可以因同路塔伤进入压力。王塔/既有深处危机仍有优先处理路径，未建立通用最优双路求解器。
4. 未识别的远端攻击不获得地面/建筑标签，不自动生成反制坐标。先最长三秒等待，随后用四费进攻/过牌底线回退。持续未知依然是功能缺口，不是“已处理”。
5. `friendly_effect=unverified` 明确写入日志。真实首次输出、牵引、目标切换/消灭仍需人工序列复核或后续友军跟踪实现。

没有修改卡组、野猪 `(113,285)` 桥点、所有既有坐标、检测模板、游戏模式、账号、付费/升级行为、既有出牌成功判据、失败重试或恢复流程。AST 比较显示，原有循环类方法仅 `_play_card`、`_use_elite_ability` 改变，新增 `_observe_confirmation`；其他原有循环类方法保持语法树一致。

## 四、验证结果及不能宣称的结果

### 已完成

- 输入 ZIP 校验，92 条 manifest SHA-256 比对，44 张冻结原图逐图查看。
- 参考 JSON 中 63/42/30/12 统计重算；案例 04 的 32 动作、六野猪、零法术重算。
- 169 项原有无需缺失夹具的策略/技能测试通过。
- 69 项新增检查通过：44 项逐图完整性与读取链路检查，25 项规则/边界/真实帧条件回放/已知缺口与隔离方法检查。与原有测试合计 238 项通过，原有 136 个 subtest 不重复加总。
- 本轮修改 Python 文件 `py_compile`。安装脚本的只读核查、临时副本应用和回退另有结果记录。

### 必须保留的限制

原包没有旧视觉测试的 `tests/fixtures/cn_battle_cues/`、`cn_threats/` 等目录；旧 `low_tower_126.png` 也缺失。第一次直接运行四个旧测试文件出现 41 个失败记录、189 passed；一部分空列表测试甚至会因缺图而“通过”，所以这一运行不能证明有效回归。缺图不能用空白图补齐，也不能暗中改断言。

`test_cn_loop_observation.py` 在导入时还缺 `pyclashbot.emulators`。本次新增循环检查从实际源码提取三个变更方法，在真实帧、假设备中执行，检验不会二次决策/点击、不会将非战斗画面喂给策略、不会用重复帧计数、技能不会抢占防守；这不是完整 ADB/状态机集成测试。

容器使用 Python 3.13.5，而项目声明 `>=3.12,<3.13`；另有 OpenCV 4.13.0、NumPy 2.3.5、pytest 9.0.2。只能报告这个环境上的离线结果，不能替代用户指定 Python 与 Windows 环境的全量回归。

本轮没有新增识别类别，因此没有宣称通过“独立场次的弩/混合空军类别验证”。现有真实帧测试中的“空中组件仍未知”是明确记录限制，不是成功识别指标。

没有新实战，没有新胜率，不能据此推断上限、声称接近 33/100 或把回放后的假想局面当作真实结果。

## 五、下一轮的最小实验与停止条件

先用完整本机项目跑所有原相关测试与新测试，并 py_compile；不要沿用容器内因缺夹具而排除的表达式。冻结全部源码/配置/模板/依赖哈希之后，固定五场工程试跑。只检查这些改动是否按预期执行，不以五场胜率证明策略效果。

优先人工核对：塔伤首次可见时刻、首次机器损伤标志、所选防守路、动作确认时刻、首个可见实际输出/牵引时刻；最后一项没有证据就写未知。确认间读取的中间帧日志包含观测和像素哈希，但原永久保存机制并未被重新实现，不能把只有哈希的中间帧当成可永久复看图像。

出现新增并发/重复点击、对消失旧坐标施法、破坏确认或恢复、重复像素增加确认计数，应立即停止候选。初始三秒远端等待结束后，在存在满足四费底线的普通可行动作时仍因相同告警无限等待，也属回退条件。比较观测间隔/P95 必须在同一台机器同口径测量；本容器没有提供 Windows 延迟改善证明。

若工程行为正确、但主要失败仍是现有模板无法识别的混合推进或无反制表的静止远程源，不继续盲目堆积长批。应先补独立场次的正反例和“有效响应/无效响应”时间序列，再决定新类别或牌型/落点修改。

最终验收不变：另行预先固定开始点，一个冻结策略连续 100 场，至少 33 场由永久原始结算图独立复核为胜利；未知与异常保留为非胜，不拼接不同候选，不删除败局。满足一次 33/100 也不是长期胜率下界的证明。
